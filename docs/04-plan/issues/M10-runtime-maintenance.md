## Milestone goal

APKRun keeps itself and its Android system up to date without touching the user's apps. An APKRun update replaces the whole APKRun.app bundle through Sparkle 2. Before Sparkle installs, apkrund closes the Android apps, stops Android, and exits. The apps reopen by themselves on the new build (D-22, [ADR-0016](../../01-architecture/decisions/0016-sparkle-host-updates.md)). An Android system update comes from a signed image feed. It downloads in the background, installs into `Images/`, and is applied when the Mac is idle: a migration A → B with a recovery point, and an automatic return to A when B fails its health check ( "runtime updater", "guest image updater").

The two host update systems are separate from each other and from Android app updates. They have their own code, state files, schedules, and UI rows. They meet only in the compatibility contract and the mutual-exclusion rule ([runtime-maintenance.md](../../02-design/runtime-maintenance.md) §2.2, §2.4). Neither writes under `Packages/` or inside a wrapper bundle. The one exception is a data schema migration, which runs as a journaled store transaction ([runtime-maintenance.md](../../02-design/runtime-maintenance.md) §1, §5).

### Goal

An APKRun update, found by Sparkle or by apkrund's probe, replaces the whole APKRun.app bundle. apkrund first closes the Android apps, stops Android, and exits. The new build starts cleanly, the apps reopen by themselves, and nothing under `Packages/`, inside the wrappers, or in the Android image changes.

### Scope

- Sparkle 2 in APKRun.app: pinning, embedding, signing, the release Info.plist keys, the settings mapping, channels, and the delegate (§3.2).
- `components.json` and the version rules (§2.1).
- The frozen `.maintenance` endpoint, `HostState` in `HelloReply`, the `maintenance` topic (§8.1, §8.3), and the self-update operations of the control endpoint (§8.2).
- `MaintenanceService`: the host states, the handshake, the marker, `BundleWatcher`, and `restartPending` (§3.5, §3.6).
- APKRun.app: `UpdateInstallCoordinator`, the install dialog, Install When Apps Are Closed, the first-launch tasks, and `AgentRegistrar` (§3.5, §3.7).
- `SchemaMigrator` and the post-update tasks (§3.8, §5).
- `SelfUpdateProbe`, its notification, the menu bar rows, and `apkrun self-update check|install|finish` (§3.4, §7.3, §7.6).
- Launcher screen U and its reconnect loop (§7.5).
- The release workflow, and the release rules R1, R5, and R6 as checks (§2.3, §3.3).
- The `maintenance.selfUpdate` health check, the markers, and the logging (§12).

Out of scope:

- Android system updates: the image-update operations, `bootPurpose`, and the Android rows of Settings (#058, #087). This task only makes `prepareForHostUpdate` refuse during `RuntimeImageState.migrating`, and it leaves the post-update hooks for the image check (§3.8 step 3, filled by #058) and the feed check (§3.8 step 4, filled by #087).
- Automatic rollback of APKRun itself (post-v1, §15). Recovery is a manual install of the previous release (§3.9).
- Notarization and the DMG (#088). Until #088 is done, the release workflow runs as a dry run and publishes nothing.
- The diagnostics bundle file `maintenance/state.json` (#060). This task provides the snapshot that #060 writes.
- The `apkrun doctor` output (#059). This task registers the check.
- The wrapper refresh operation (#076). This task shows the prompt that calls it.

5. **`MaintenanceService` (design step 5).** Add the actor in RuntimeHost. ### Goal

An Android image B, given as a signed `.aar` file, is installed next to the current image A and applied as a migration: Android boots B with the existing userdata, or returns to A with the data unchanged when B fails. After a successful migration, the user can go back to A.

### Scope

- The version and compatibility checks and the migration data steps of [android-image.md](../../02-design/android-image.md) §12.1–§12.3.
- `ImageUpdateCoordinator` with the phases `idle`, `ready`, `applying`, and `failed`, `Images/update-state.json`, and the startup reconciliation (§4.3).
- `RuntimeSupervisor.migrateImage(to:operation:)` with the additions of §4.7.
- The archive install `ImageStore.install(from:.archive)` (§4.5, [../../03-reference/runtime-image-manifest.md](../../03-reference/runtime-image-manifest.md) §8.3) and the manual install: `installImage(.file)`, `apkrun image install <file.aar>`, **Install from File…**.
- The user-initiated apply with its dialog (§4.6).
- Rejected versions, rollback, and GC (§4.8, §4.9).
- An incompatible current image, without the feed part (§4.10).
- `image list`, `recovery-points list|delete`, the Storage rows, the migration header text, the failure notification (§7.2–§7.4, §7.6).
- `maintenance.imageUpdate` (the rejected and incompatible rows), the image markers, and the `imageUpdate` log category (§12).

Out of scope:

- The image feed, downloads, candidate selection, the automatic apply gate, ask mode, reminders, and the feed checks of the install (#087).
- `apkrun image check` and `image install --latest` (#087).
- The Android status lines and settings of Settings → General, the "Android system update ready" notification, and its menu bar row (#087).
- Delta image updates (post-v1, §15).
- Building new release images. The image release candidate procedure is [../test-strategy.md](../test-strategy.md) §9.3.

- **Pitfall:** `SuspendingClock` stops while the Mac sleeps, so the 15-minute timeout is not used up by sleep. The VM is paused then ([runtime-daemon.md](../../02-design/runtime-daemon.md) §6).
- The archive install is built here and not in #087. §13 says "#058 works with local image files", and design step 3 installs `<file.aar>`, which needs the extraction. #087 adds only the feed checks (the archive SHA-256 against the feed entry, and the manifest against the entry) and the deletion of the downloaded archive. This is a choice of this plan (see the M10 report).
- A manual install has no `expandedSize`. Its space rule (the file size + 10 GiB before, and at least 10 GiB left during extraction) is in [../../03-reference/runtime-image-manifest.md](../../03-reference/runtime-image-manifest.md) §8.3.
- **OQ-41** ([../open-questions.md](../open-questions.md)) is a Decision due before this task starts. With the working default, v1 has no restore for the recovery point that Reset Android (#066) creates: `recoveryPoints` lists it with `reason =.resetAndroid`, `deleteRecoveryPoint` deletes it, and apkrund prunes it after 7 days. `rollbackImage` restores only the recovery point of the last migration. If the answer is yes, this task also adds the restore operation, its CLI command, and **Restore…** in Settings → Storage, and updates [../../02-design/runtime-daemon.md](../../02-design/runtime-daemon.md) §9.5 and [../../03-reference/runtime-api.md](../../03-reference/runtime-api.md) §12 in the same pull request.
- Bootconfig sets only `ro.boot.*` properties, so bundle B carries `androidboot.apkrun.test.marker=B`, and the T2 test reads `ro.boot.apkrun.test.marker` ([../../02-design/android-image.md](../../02-design/android-image.md) §12.4).

### Goal

Android system updates arrive by themselves. apkrund reads a signed image feed, picks a compatible newer image, downloads it in the background, installs it, and applies it when the Mac is idle, or when the user asks. A new install of APKRun gets its first image from the same feed.

### Scope

- The release pipeline for images: the archive, the feed entry, feed signing, the weekly re-signing, publishing (§13 #087 step 1).
- `ImageFeedClient` with the rules of §4.1.
- The check schedule and candidate selection C1–C7 (§4.2), and the `available`, `checking`, `downloading`, and `installing` phases (§4.3).
- `ImageDownloader` (§4.4) and first-run provisioning from the feed ([runtime-daemon.md](../../02-design/runtime-daemon.md) §9.3).
- The feed checks of the archive install and the R-25 measurement (§4.5).
- The automatic apply gate A1–A7, ask mode, reminders, and critical entries (§4.6), and the feed part of §4.10.
- `apkrun image check`, `image install --latest`, the Android part of Settings → General, the notifications, and the menu bar row (§7).

Out of scope:

- Delta image updates (post-v1, §15).
- The migration, the archive extraction, rollback, and GC (#058).
- The updates host and the real upload (OQ-01). Until OQ-01 is settled, publishing runs as a dry run.
- Building the release `-user` image itself. That is the image release candidate procedure ([../test-strategy.md](../test-strategy.md) §9.3).

### Deliverables

- `scripts/release/image-feed.py` (`add`, `resign`, `--key`, `--base-url`, `--dry-run`), `.github/workflows/image-release.yml`, and `.github/workflows/image-feed-resign.yml`.
- `ImageFeedClient` and `ImageDownloader` in `Packages/ImageCore/Sources/ImageCore/Updates/`.
- The check schedule, candidate selection, and apply gate in `ImageUpdateCoordinator`, and the rest of the `Images/update-state.json` fields of §4.3.
- The control operations `checkImageUpdate`, `downloadImageUpdate`, `cancelImageDownload`, and `installImage(.latest)`.
- `apkrun image check [--json]` and `image install --latest [--yes]`.
- The Android controls and status lines of Settings → General, the onboarding download, the notifications, and the menu bar row.
- The feed fixtures in `Tests/Fixtures/runtime-updates/image-feed/` (valid, tampered, replayed sequence, expired) and `scripts/dev/image-feed-server.py` with `Range` support.
- T0, T1, and T2 tests, and the R-25 result.

### Implementation steps

The design steps are [runtime-maintenance.md](../../02-design/runtime-maintenance.md) §13 #087, steps 1–8. The steps here follow them one to one. Step 5 is smaller than design step 5, because #058 built the archive extraction.

1. **Release pipeline (design step 1).** On a Mac, pack a bundle signed with the release image key with `aa archive -a lzfse` ([../../05-development/build-system.md](../../05-development/build-system.md) §10.2). `scripts/release/image-feed.py add --channel <c> --archive <aar>` builds the entry from the bundle's manifest (`imageVersion`, `requirements`, `userdata`, `upgradeFrom` from `compatibility.upgradeFrom`), the archive (`size`, `sha256`), and `expandedSize` (the sum of the regular files, [../../03-reference/runtime-image-manifest.md](../../03-reference/runtime-image-manifest.md) §8.1). It raises `sequence`, sets `generatedAt` and `expiresAt = generatedAt + 30 days`, and signs the exact bytes into `feed.json.sig` with the format of `manifest.sig`. Before it writes, it checks R3 and the rules of [../../03-reference/runtime-image-manifest.md](../../03-reference/runtime-image-manifest.md) §9.4. `image-feed.py resign` signs both channels again with a new sequence. Add `image-release.yml` (manual) and `image-feed-resign.yml` (weekly, `ubuntu-latest`) ([../../05-development/build-system.md](../../05-development/build-system.md) §15.1, [../../05-development/workflow.md](../../05-development/workflow.md) §10). Both run with `--dry-run` until OQ-01 is settled. Write the committed fixtures with `test-image-ed25519`. Check: a feed written by the script passes the T1 client validation, and the release check refuses a manifest with an `androidboot.apkrun.test.*` key.
2. **`ImageFeedClient` (design step 2).** Fetch `<base>/<channel>/feed.json` and `feed.json.sig` over HTTPS with the limits and the ETag of rule 1. The base URL is the Info.plist key `APKRunImageFeedBaseURL`, set by the Release build and absent in Debug. Check the signature against `ImageTrustStore` before parsing, then the channel, the sequence and its byte identity, the expiry, the schema version, and the field rules ([../../03-reference/runtime-image-manifest.md](../../03-reference/runtime-image-manifest.md) §9.2–§9.4). A refused feed keeps the last accepted one in effect. Store the highest sequence per channel in `Images/update-state.json`. Send no identifiers, only the `User-Agent` of §10. Update the "Image feed" section of the manifest reference if the implementation shows a gap. Check: the T0 feed validation tests pass.
3. **Schedule and candidates (design step 3).** Check every 24 hours ± 1 hour at the hourly wake or while apkrund runs (only with `maintenance.checkAutomatically`), when APKRun.app connects (at most every 6 hours), right after an APKRun update (#057's §3.8 step 4 hook) or a channel change, and on **Check Now** or `apkrun image check` (user-initiated). Retry a failed check after 1 hour, then 6 hours, then on the daily schedule. A check never starts Android and is not runtime activity. Select the candidate by C1–C7 (§4.2). Remember a C2 failure as `requiresNewerAPKRun(version)`. Compute the C6 bucket from the instance ID in `state.json`, and ignore it for user-initiated checks and `critical` entries. `imageUpdateStatus` lists the gate conditions that are false. Check: the T0 selection tests pass, including 10,000 random instance IDs within ±2 % of the rollout percentage.
4. **`ImageDownloader` (design step 4).** Download into `Cache/images/<imageVersion>.aar.partial` and hash while downloading. Resume with `Range` and `If-Range`, hash the partial file again before resuming, start over on a `200`, and stop with `imageArchiveSizeMismatch` above `size`. Rename to `.aar` when size and hash match (`imageArchiveHashMismatch` otherwise). Check the space (archive + `expandedSize` + 10 GiB) before the download and before the install (`insufficientSpace`). Apply the network rules of §4.4, wait in Low Power Mode, and download in the background only with `maintenance.downloadImagesAutomatically`. A user-initiated download on an expensive or constrained network asks first: "This download is ‹1.8 GB›. You're on a network that may charge for data." A download is an operation in flight, so apkrund does not exit. It resumes 2 minutes after wake. Retries follow §4.3 (15 minutes, 1 hour, 6 hours). **Cancel** keeps the partial file. Partials older than 7 days, or replaced by a newer candidate, are deleted. Add first-run provisioning from the feed ([runtime-daemon.md](../../02-design/runtime-daemon.md) §9.3): onboarding step 3 shows "Download Android (‹size›)" with a progress bar in release builds ([host-ui.md](../../02-design/host-ui.md) §4); the first download ignores the rollout and the expensive-network rule but asks first on an expensive network. Check: the T1 downloader tests against `scripts/dev/image-feed-server.py` pass.
5. **Feed install and R-25 (design step 5).** For a feed install, check the archive SHA-256 against the entry before extraction (`imageArchiveHashMismatch`), and after verification compare the manifest's `imageVersion`, `requirements`, and `userdata` with the entry (`imageFeedInvalid`) ([../../03-reference/runtime-image-manifest.md](../../03-reference/runtime-image-manifest.md) §8.3 steps 1, 3, and 6). Delete the archive from `Cache/images/` after the install. A verification failure deletes the archive and downloads it once more. After a second failure, nothing is retried until the feed changes. Store `securityPatchLevel` and `tzdataVersion` with the installed version. Measure R-25 on the reference Mac with a release-size archive: the wall time of the install, and the bytes written from `proc_pid_rusage` (`ri_diskio_byteswritten`). Build the sparse-aware extraction sink if the install takes more than 5 minutes or writes more than twice `expandedSize`. Otherwise, set R-25 to `accepted` with the numbers. Check: R-25 is no longer `open`.
6. **Apply gate and reminders (design step 6).** Evaluate A1–A7 (§4.6) every 5 minutes while an image is `ready` and apkrund runs, on the events that can open it (a session ended, the power source changed, an activity was released), and at the hourly wake. apkrund does not stay alive only to wait. Read the idle time from `HIDIdleTime`, the power source from IOKit power sources, Low Power Mode and `thermalState` from `ProcessInfo`. In Debug, `APKRUN_TEST_IDLE_SECONDS` and `APKRUN_TEST_POWER` replace them. Store `lastAutomaticApplyAt` for A7. Ask mode posts "Android system update ready" once with **Update Now** and **Later**, and reminds after 7 days (1 day for a `critical` image). In automatic mode, an image `ready` for 7 days (1 day if critical) gets the same notification. After a successful automatic update, post "Android was updated to ‹B›" only with `maintenance.notifyImageInstalled`. Add the feed part of §4.10: check at once, download without the network rules, and apply as soon as the image is `ready`, ignoring A4, A5, and A7. With no compatible image, report `noCompatibleImage` with the link to the downloads page. Check: the T1 coordinator tests with fakes pass for the gate, ask-mode reminders, and a rejected version that is skipped.
7. **Surfaces (design step 7).** Add `apkrun image check [--json]` (exit 0, with the phase, the candidate, and any `requiresNewerAPKRun`) and `apkrun image install --latest [--yes]`, which downloads, installs, and applies, whichever steps are still needed. Ctrl-C during its download cancels and keeps the partial file. It asks before retrying a rejected version. In Settings → General, add the Android controls (install mode, background downloads), the version line with the security patch level (§4.11), **Check Now** for both systems, and the Android status lines of §7.1 with **Update Android Now…**, **Cancel**, **Install Update…**, **Try Again**, and **Report a Problem…**. Add the menu bar row "Android system update ready" with **Update Now**. Extend `maintenance.imageUpdate` with the rows of §12 for the feed, the download, the ready state, and the space. Emit `IMAGE_CHECK_END`, `IMAGE_DOWNLOAD_START`, and `IMAGE_DOWNLOAD_END`. Check: checklist item C05-6 passes.
8. **Acceptance (design step 8).** (a) T1 against `scripts/dev/image-feed-server.py` serving `Tests/Fixtures/runtime-updates/image-feed/`: a valid feed selects the right candidate for each of C1–C7; a tampered feed, a replayed sequence, and an expired feed are refused; a download interrupted at 50 % resumes and gives the same SHA-256; not enough space is reported before the download starts. (b) T2 on the lab Mac with a Debug build: image A is installed, and a local feed offers B, signed at run time with the lab key (`image-feed.py --key`). `APKRUN_TEST_IMAGE_FEED_URL` points apkrund at the server. apkrund downloads B in the background and applies it once the gate opens (`APKRUN_TEST_IDLE_SECONDS=900`, `APKRUN_TEST_POWER=ac`), and HelloText's data is kept. Check: every acceptance criterion is checked.

### Tests

By tier ([../test-strategy.md](../test-strategy.md)):

- **T0** (`Packages/ImageCore/Tests/ImageCoreTests/`, `Packages/RuntimeHost/Tests/RuntimeHostTests/`): feed validation (signature, channel, sequence, expiry, unknown fields, unknown schema, duplicate versions) and the manifest–feed agreement; candidate selection C1–C7 with the rollout bucket distribution; the check schedule and backoff with a fake clock; the gate A1–A7 table; the `maintenance.imageUpdate` rows of this task.
- **T1**: the downloader against a local HTTP server (resume with `Range` and `If-Range`, a `200` reply to a range request, a server that sends too many bytes, a hash mismatch, cancel and resume); `ImageUpdateCoordinator` with a fake store, a fake supervisor, and a fake clock (every transition of §4.3, a restart in each persisted phase, the gate, ask-mode reminders, a rejected version that is skipped); the #087 step 8a feed tests; a feed written by `image-feed.py` accepted by the client.
- **T2** (`Tests/IntegrationTests/MaintenanceTests/`, CI job `maintenance`): the feed-driven update on the lab Mac (step 8b).
- **T3**: checklist C05-6 (the ask-mode reminder, the install, the restart text); the release smoke matrix with the current and the previous stable image from the published feed ([../test-strategy.md](../test-strategy.md) §9.2), once OQ-01 is settled.

### Acceptance criteria

- [ ] Against the local feed server, a valid feed selects the right candidate for each of C1–C7, and the rollout bucket of 10,000 random instance IDs is within ±2 % of the percentage.
- [ ] A tampered feed, a replayed sequence, and an expired feed are refused, and the last accepted feed stays in effect.
- [ ] A download interrupted at 50 % resumes and gives the same SHA-256. Not enough space is reported before the download starts.
- [ ] On the lab Mac, with image A installed and a local feed offering B, apkrund downloads B in the background, applies it once the gate opens, and HelloText's data is kept.
- [ ] An image is never applied automatically while a session, an activity, or a store operation exists, and never while the host state is not `normal`.
- [ ] Checks and downloads never start Android and never run on the launch path (NFR-PERF-07).
- [ ] A release build with no image gets its first image from the feed during onboarding, with the size and a progress bar.
- [ ] `image-feed.py` writes a signed feed that the client accepts, and `image-release.yml` and `image-feed-resign.yml` pass a dry run.
- [ ] R-25 is not `open`, and the install time and bytes written are recorded.
