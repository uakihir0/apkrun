# Default-profile stall diagnosis (#064, 2026-10-08)

Scope: why the `default` profile (and, by identical bootconfig, the
`swiftshader` profile) never reached `sys.boot_completed=1`. The raw captures
are retained outside the repository because they are large (host logcat up to
13.7 MB). Each is normalized by `capture.sh` and contains no host paths; the
SHA-256 values below identify the retained files.

## Setup

- Reference host: Ubuntu 24.04.4 arm64 nested-virtualization VM, 8 host vCPUs,
  15 GiB RAM. Cuttlefish 1.57.0 (VCS `9bb9c72329cedcb436bb75afc05c24d73fbcdf5d`),
  build 16373615 product images verified against the checked-in manifest.
- Capture script: `Images/tools/reference/capture.sh`, last changed by
  `fe1c726` (host logcat collection). The runs used the repository tools at
  HEAD of `codex` on 2026-10-08 without a tool change.
- Profile flags as in android-image.md §8.2: `default` = 4 guest vCPUs,
  4096 MiB, `selectedGpuMode=guest_swiftshader`, vhost-user GPU off, console off,
  boot observer on (`APKRUN_CAPTURE_BOOT_OBSERVER=1`).
- Instance 2 was used because a stale instance-1 group (from an earlier target
  run) still held instance 1 in the CVD registry; it was left untouched.

## Failure mechanism (E1)

Each `system_server` cycle ended with the framework Watchdog killing it after
its main thread failed to answer a handler check for about 185 seconds.

- Cycle 1: the Watchdog's annotated main-thread stack ended in
  `ArtManagerLocal$Injector.getDexoptHelper` (`ArtManagerLocal.java:1807`), and
  the main thread had entered `ArtManagerLocal` only about four seconds before
  the kill. Other threads reported long monitor contention on
  `WindowManagerService.displayReady`, `ActivityManagerService` and
  `SettingsProvider`.
- Cycle 2: `SystemServerTiming` recorded `StartAudioService took 54296ms`;
  the Watchdog's annotated top frame was
  `FakeSoundTriggerHal.createDefaultProperties` (`FakeSoundTriggerHal.java:617`).

The blocking code differs between cycles, so no single code path was
identified. After the first kill, init sent SIGKILL to zygote and to the
services in its class (audioserver, cameraserver, media, netd), and zygote
restarted.

`artd` is a lazy service (`disabled` plus `interface aidl artd`). It was not
running and not registered (`service check artd` returned not found), and no
init start request for `aidl/artd` appears in the logs. This is recorded as an
observation, not as the cause: the blocked frame differed between cycles.

Cycle 1 preload took 371 s; cycles 2 and 3 took 26 s and 18 s. The first
cycle's cost is consistent with cold page-cache reads, which is not
established.

## Host-side evidence

- Host crosvm RSS (boot observer, E0) reached about 4.2 GiB about 70 s after
  launch and stayed near that value. The observer recorded 118 crosvm memory
  samples in E0 and about 120 in the earlier `target` record.
- Host-side per-thread CPU sample of the Android crosvm (10 s, E1,
  06:11:10-06:11:25 UTC): this falls after the U-Boot banner (06:09:28 UTC)
  and before Linux, inferred from zygote start minus its uptime; the exact
  boot phase is not identified. `vcpu0` used about 86% of one CPU;
  `vcpu1`-`vcpu3` used under 15% combined. Zygote's main thread (E0,
  06:03 UTC, preload) alternated between `R` and `D` states.
- Guest CPU during E1 cycle 2 (about 06:50 UTC, before the second kill): load
  average about 10 on 4 vCPUs; over 10 s, idle was about 0%, and system plus
  IRQ time was about 53% of busy time. `system_server` accumulated about 1300
  system ticks per 10 s.
- Guest I/O pressure (`/proc/pressure/io`) was low (some avg10 about 2%).

## Ruled out or not supported

- Host-side stall of crosvm or vCPUs: not supported; progress continues and
  host vCPU threads run.
- SurfaceFlinger EGL failure (the `target` failure): not present; SurfaceFlinger
  initialized ANGLE on SwiftShader and started the boot animation in both
  runs.
- Zygote hang in preload: not present; preload completed in E1.
- Missing `system_server` logs: caused by the older capture revision, which did
  not collect host logcat; the current revision does.
- Observer crosvm sampling failure: not present; samples were recorded.

## Not established

- The root cause of guest-wide slowness. Candidates are nested-virtualization
  overhead (high guest system and IRQ time), cold-cache I/O in the first cycle,
  and vCPU count. The 8-vCPU variant (E2) tests the vCPU count only.
- The exact main-thread block in each cycle. Java thread stacks need root;
  `adb root` and `debuggerd` were refused (`ro.secure=1`).

## Next step

Obtain root-readable `system_server` thread dumps for a boot that reaches
the Watchdog window, through a diagnostic-only route that does not change the
pinned image, and compare a second boot on warm caches. Failing that, the
reference-host choice in android-image.md §8.1 (bare-metal arm64 Linux) is the
path that removes the nested-virtualization overhead.

## Repeat run with the intended 8-vCPU change (E2)

The E2 scratch copy changed `launch_profile` for `default` from `--cpus 4` to
`--cpus 8` on `cvd create`. The retained configuration and launcher log both
record 4 vCPUs (`"cpus" : 4`, `--cpus=4`), so the change did not reach the
guest. E2 is therefore a repeat of the 4-vCPU `default` profile, not a test of
vCPU count. The CPU-count hypothesis stays open; a retry must pass the count to
`cvd start` as well and confirm `cpus` in the saved configuration.

Its timeline, however, differs from E1 under the same flags:

The first `system_server` in E2 was still in PackageManager when its 3000-second
deadline expired, so E2 shows no Watchdog kill. It also shows that run-to-run
variance under identical flags is large: the same boot path took about 1.7
times longer here than in E1. The `kernel.log` of E2 was at a 10,308-byte
U-Boot-only stage (`Starting kernel ...`) for several minutes before Linux
started, which the earlier 2026-10-02 records also showed under other flags.
